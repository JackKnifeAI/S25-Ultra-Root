## Vulnerability Analysis (from firmware RE)

### Vulnerable Function: 0xea0 in spu_service.mbn
- Frame: 176 bytes (0xb0)
- Buffer at sp+40, canary at sp+88
- Overflow offset: 48 bytes

### Exploitation Flow
1. Message delivered via SEND_MODIFIED with 18-byte inline format (CONFIRMED: ret=18)
2. cmd_index=2 with param=0x11 reaches vulnerable function
3. Function calls 0x17fc to read from SPU secure storage
4. If storage read FAILS → error path → copies data to sp+40 without bounds check
5. Copy exceeds 48 bytes → corrupts stack canary → SPU crash

### Current Blocker
- Function 0x17fc succeeds on provisioned phone (secure storage service 9 is available)
- Success path returns without triggering the overflow
- Need storage read to FAIL to enter error path

### Potential Attack Vectors (To Explore)
1. **Different cmd_index:** Try all 19 dispatch entries — some may reference non-provisioned storage
2. **Service exhaustion:** Flood the SPU with requests to exhaust service 9 resources
3. **Race condition:** Kill storage service between registration and read
4. **cmd_index=3 (param=0x111):** Goes through 0x1aa4 first, then calls 0xea0 with different params
5. **Direct overflow path:** Look for OTHER callers of 0x3b0 that don't go through 0x17fc

## Deep RE Analysis (Agent Results — August 4, 2026)

### Root Cause: Integer Truncation (CWE-120)
```
0x101c: ldr w2, [sp]       ; 32-bit load truncates high bits
0x1020: cmp x2, x21        ; 64-bit compare — truncated value passes bounds check
0x1024: b.ls 0x1040        ; if truncated <= data_size → copy proceeds (OVERFLOW!)
```

The size validation uses `ldr w2` (32-bit) but compares with `cmp x2` (64-bit, zero-extended).
If the stored size has upper 32 bits set, truncation causes the check to pass incorrectly.

### Function Call Chain
```
0xea0 (vulnerable function)
  → 0xf34: memset(dma_buf, 0, size)     — ZEROES our DMA data!
  → 0xf48: bl 0x17fc                     — read from SPU storage
  → if 0x17fc fails:
    → 0xf8c: memset(dma_buf, 0, size)   — wipe again (redundant)
    → 0xf9c: bl 0x1974                   — send error response
    → if 0x1974 succeeds:
      → 0xff8: bl 0x3b0 (w1=2,w3=0x10) — FIRST CALL (currently FAILS: w3 mismatch!)
      → if first call succeeds:
        → 0x1068: bl 0x3b0              — SECOND CALL: copies to sp+40 (OVERFLOW!)
```

### Why the Overflow Doesn't Trigger (Current Understanding)
1. **0x17fc succeeds** — TSID/STTA storage exists on provisioned phone
2. **Even if 0x17fc fails** — first call at 0xff8 fails (w3=0x10 vs expected 0x11)
3. **The second call (overflow) is only reached when BOTH conditions are met:**
   - 0x17fc fails (storage error)
   - First call succeeds (depends on runtime state of x26)

### Resource Exhaustion Vector
The SPU has a global counter at 0x10068 that increments on each `spu_get_shared_mem()` call
but is **never decremented** in analyzed code paths. This is a potential resource leak.
Repeated spcom open/send/close cycles could exhaust SPU resources, eventually causing
`spu_storage_channel_open` to return 0 (failure), triggering the error path.
